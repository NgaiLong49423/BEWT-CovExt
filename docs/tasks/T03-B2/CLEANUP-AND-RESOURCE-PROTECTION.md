## Route-isolation candidate safety — offline only (r55)

The candidate uses a non-internal bridge with Docker IP masquerading disabled and explicit recorded IPAM. App/browser containers are created with a dormant bootstrap, exact run labels, pinned image references, loopback-only published ports, no mounts, `HostConfig.Privileged=false`, and no added persistent capabilities. After exact ID/image/name/label/network/port inspection, the approved one-shot route command is `docker exec --privileged --user 0 <recorded-full-container-id> /bin/sh -c 'ip route del default'`. Docker documents `--privileged` as granting extended privileges to that exec process; therefore the process is elevated for this single command even though the persistent container configuration stays unprivileged ([Docker exec reference](https://docs.docker.com/reference/cli/docker/container/exec/)). The runner then requires empty IPv4/IPv6 default-route output and blocked external TCP probes before starting services. This behavior and cleanup path have only offline unit/fault coverage; no Docker runtime has tested them.

Cleanup remains exact-record-only: verify complete ownership labels, recorded container IDs/names, exact image references, network ID/project/IPAM and endpoints, mount/volume ownership, and residual resources; block on unknown inspect/daemon/permission errors or any remaining task-run resource. No global prune or unrelated resource removal is permitted. The new candidate has not created any Docker resources.

The later Sonar correction changes startup logs from shared `/tmp` paths to a new directory created by `mktemp -d` under the container user's home with `umask 077`; it verifies that `$HOME` is a real directory rather than a symlink and validates the returned path before writing or reading the service log. This and the route candidate pass offline checks in `evidence/offline-verification-20261109-r57/`; runtime behavior remains untested.
