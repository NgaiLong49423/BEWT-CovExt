# Source Reuse and Gaps

## Existing assets reused

- `framework/src/runtime/workflow.ts`: shared LangGraph role nodes, SQLite checkpoints, human-review interrupt/resume, revision loop, execution and a two-repair ceiling. Integration coverage includes `framework/test/integration/workflow.test.ts` (REVISE→fresh checkpoint→ACCEPT, REJECT before Java, thread/replay protection, two bounded repair artifacts, and process restart).
- `framework/src/runtime/tool-dispatcher.ts`, `safe-path.ts`, `maven-command.ts`, and `process.ts`: fixed tool schemas, contained paths and fixed Maven/process launchers.
- `framework/src/contracts.ts` and `policy.ts`: parsed baseline/candidate/review/validation provenance, current-revision approval and separation between technical eligibility and research acceptance.
- `adapters/expresscart/experiment.ts`: ExpressCart-specific source/image pinning, Docker ownership, fixture lifecycle, invocation cleanup/recovery and evidence. T01-C adds generated-class operations while preserving T01-B behavior.
- `experiments/expresscart/bewt-suite/pom.xml`, `src/test/java/tests/BaseTest.java`, and `src/main/java/po/PageObject.java`: baseline build/dependency/test foundation. Static inventory found no existing password-reset/forgotten-password Page Object matching this candidate, so `adapters/expresscart/java/CustomerPasswordResetPage.java` adds a source-grounded adapter Page Object for the reset-token path. The isolated harness stages only the POM, PageObject base, that exact adapter Page Object, BaseTest, and registered generated class. It records hashes for these files and excludes historical tests/application source.
- `experiments/expresscart/agent/src/sprint03-generator.ts` and `sprint03-langgraph-repair.ts`: historical implementation patterns only, not a parallel execution path.

## T01-C changes to former assumptions

- `framework/src/cli.ts` remains the T01-B entry point and still uses the historical EC-C04 flow. T01-C has its own shared-workflow entry point, `framework/src/t01c-cli.ts`, so the accepted T01-B CLI behavior is not silently changed.
- T01-C candidate IDs are generated by `newCandidateId()` and revisions retain that candidate identity. The T01-C coverage analysis currently proposes one fixed, source-backed *behavior* (`customer.password.reset.invalid-or-expired-token`) for the ExpressCart pilot; it is not an 8-app analysis and is not a fixed EC-C04 candidate.
- Historical overlap input is now read from `data/coverage/expresscart/historical-candidate-behavior-index.json`, indexed by `data/coverage/expresscart/index.json`, and parsed by `adapters/expresscart/historical-behavior-index.ts`. The five EC-C01..05 behavior IDs link to Sprint 02 revised Gherkin and Sprint 03–05 review/outcome records; they are explicit overlap cues, not semantic novelty judgments.
- The old adapter mapping `EC-C04 → tests.ForgottenPasswordTest` remains only for T01-B compatibility. T01-C registry uses deterministic class names from candidate ID/revision (`framework/src/runtime/java-class.ts`) and verifies the exact registered artifact/hash before Maven selection.
- T01-C uses source-backed fixture profiles in `resolveExpressCartFixtureProfile()`; invalid/expired reset token execution is designed not to mutate a customer record. The legacy EC-C04 fixture remains intact. Profile selection and harness file staging are unit-tested; live generated-candidate fixture execution is NOT_RUN.
- T01-C evidence routes to `docs/tasks/T01-C/evidence/`; T01-B evidence routing remains unchanged.
- `framework/src/runtime/model-provider.ts` now contains fake and Gemini Gherkin/Java provider contracts, output schemas, timeout, one-attempt/no-retry behavior, model allowlist, output caps and telemetry. Live Gherkin call failed authorization; Java provider has not been called.
- `framework/src/runtime/java-artifact-registry.ts` creates an immutable candidate/revision/source registration. `adapters/expresscart/generated-test-harness.ts` stages the manifest POM, `BaseTest`, and exact registered class only; its copy policy is tested and actual offline Maven `test-compile` is evidenced.

## Remaining gaps and evidence limits

- The current source claim and historical candidate index are ExpressCart-specific; the baseline remains the pinned Sprint 01 sanitized feature/test inventory with route-derived tags. Neither exact-tag comparison nor the historical index establishes semantic novelty, and this is not generalized to seven other apps.
- No live Gemini candidate, real human review decision, Gemini Java artifact, Selenium E2E, cleanup outcome, repair attempt, or T01-C actual `ValidationResult` exists. The offline Maven compile used a fake provider and is not model evidence.
- Filesystem-only traversal/symlink checks in `framework/test/integration/tool-boundaries.test.ts` and the ExpressCart evidence-discovery test passed outside the managed sandbox (3/3). The full adapter lifecycle test still cannot run because Docker Desktop's daemon is unavailable.
- Historical Sprint 01–05 metrics and `bewt-original/` remain read-only. No application source or Docker configuration was changed.
